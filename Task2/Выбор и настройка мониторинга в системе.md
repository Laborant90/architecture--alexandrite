**Мотивация**

Необходимо понять как внедряемые изменения помогут решить текущие проблемы системы. Для этого предлагаю отслеживать следующие показатели:

1. Отслеживание количества заказов полученных через АПИ (заказы поступают от различных пользователей АПИ - для каждого из них рассчитывается нагрузка в виде показателя RPS (количество запросов в секунду)). По показателям метрики можно понять какие из пользователей АПИ больше нагружают АПИ. Можно понять какое количество ресурсов необходимо для поддержки текущего объема запросов (можно настроить автоматическое масштабирование).
2. Отслеживание смены статусов заказов (в любой из частей системы) - метрика меняется при любой смене статуса, что позволяет в реальном времени контролировать ход обработки. Например: за день было подтверждено (SUBMITTED) 1000 заказов, а посчитана стоимость только для 100 - что говорит о задержке расчёта стоимости на MES.
3. Количество заказов в очереди - позволяет увидеть насколько загружена очередь
4. Количество заказов на операторе - позволяет увидеть насколько загружены операторы
5. Время обработки запроса в MES - позволяет увидеть как долго обрабатываются запросы к MES.
6. Время нахождения запроса в очереди - позволяет увидеть скорость обработки запроса

**Выбор подхода к мониторингу**

В качестве подхода к мониторингу предлагаю использовать RED. Метод RED, фокусируется на трёх показателях: на частоте запросов, длительности их обработки и ошибках. Эти показатели помогают обеспечить стабильную работу веб-сервисов и API. Так как проблемные места сервиса связаны с API этот метод лучше всего подойдёт.

Для мониторинга инфраструктуры предлагаю использовать USE.

**Метрики**:

1. Количество заказов полученных через API - нужна для понимания внешней нагрузки на систему
Ярлыки: тип апи (MES API/Shop API), инициатор заказа (внешний/внутренний)
2. Смена статуса заказа - нужна для понимания как меняются статусы заказа в различных частях системы.
3. Количество заказов в очереди - позволяет увидеть насколько загружена очередь.
Ярлыки: инициатор заказа (внешний/внутренний)
4. Количество заказов на операторе - позволяет увидеть насколько загружены операторы.
Ярлык: идентификатор оператора
5. Время обработки запроса в MES - позволяет увидеть как долго обрабатываются запросы к MES.
Ярлык: инициатор заказа (внешний/внутренний)
6. Время нахождения запроса в очереди - позволяет увидеть скорость обработки запроса
Ярлык: инициатор заказа (внешний/внутренний)

**Метрики технических показателей очереди RabbitMQ**

1. Объём данных в очереди - очередь может быть ограничена по объёму содержащихся в ней данных, а переполнение при определённых настройках может приводить к удалению сообщений. Метрика предупредит о приближении к заданному лимиту.
2. Количество сообщений в очереди - скопление сообщений может говорить о проблемах на потребителях. Например, потребители вышли из строя, деградировали или их текущей пропускной способности перестало хватать для возросшей нагрузки.
3. Количество потребителей на очереди - метрика поможет заметить выход обработчиков из строя, даже если в обменах тишина и очереди не растут — то есть до того, как это станет проблемой.
4. Наличие немаршрутизируемых сообщений - показатель позволит узнать о потере сообщений из-за недочётов в топологии.
5. Наличие сообщений в DLX - метрика поможет заметить проблемы в обработке сообщений и среагировать на них.

**Метрики технических показателей микросервисов k8s**

1. CPU / Memory Requests vs Actual Usage - Метрика «фактическое использование» отслеживает, сколько ресурсов использует под во время работы, при этом считается комбинация ресурсов: деплойментов, Statefulset и других.
2. CPU / Memory Limit vs Actual Usage - Метрика отслеживает запросы ресурсов, которые используются планировщиком для планирования рабочих нагрузок на нодах. Лимиты ресурсов позволяют устанавливать границы их использования во время выполнения рабочих нагрузок. Метрика важна так как позволяет понять, какие последствия наступают при превышении лимитов CPU и памяти.
3. Percentage of Unavailable Pods Out of Desired Replicas - метрика отслеживает количество реально развернутых подов vs желаемое. При развертывании приложения задается число желаемых реплик (подов), которое оно должно запустить. Наличие недоступных подов — это ненормальное состояние системы. Оно может проявиться в любой момент — от небольшого сбоя до полной недоступности службы. Результат зависит от доли недоступных подов из количества желаемых реплик и важности недостающих подов в основных потоках системы.
4. Desired Replicas Out of HPA Maximum Replicas - Горизонтальное автомасштабирование подов (HPA) — это ресурс Kubernetes, который позволяет корректировать количество реплик, выполняемых рабочей нагрузкой в соответствии с определенной вами целевой функцией. Распространенный сценарий использования — автомасштабирование среднего использования ресурсов CPU подами в деплойменте по сравнению с запросами CPU. Когда количество реплик в деплойменте достигает максимума, определенного в HPA, может возникнуть сложная ситуация. Вам понадобится больше подов, но HPA не может масштабировать.
5. Метрики JVM для анализа показателей Java микросервисов (использование CPU/RAM, сборка мусора)
6. Метрики ASP.NET для анализа показателей .NET микросервисов
