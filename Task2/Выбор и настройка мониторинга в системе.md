**Мотивация**

Необходимо понять как внедряемые изменения помогут решить текущие проблемы системы. Для этого предлагаю отслеживать следующие показатели:

1. Отслеживание количества заказов полученных через АПИ (заказы поступают от различных пользователей АПИ - для каждого из них рассчитывается нагрузка в виде показателя RPS (количество запросов в секунду)). По показателям метрики можно понять какие из пользователей АПИ больше нагружают АПИ. Можно понять какое количество ресурсов необходимо для поддержки текущего объема запросов (можно настроить автоматическое масштабирование).
2. Отслеживание смены статусов заказов (в любой из частей системы) - метрика меняется при любой смене статуса, что позволяет в реальном времени контролировать ход обработки. Например: за день было подтверждено (SUBMITTED) 1000 заказов, а посчитана стоимость только для 100 - что говорит о задержке расчёта стоимости на MES.
3. Количество заказов в очереди - позволяет увидеть насколько загружена очередь
4. Количество заказов на операторе - позволяет увидеть насколько загружены операторы
5. Время обработки запроса в MES - позволяет увидеть как долго обрабатываются запросы к MES.
6. Время нахождения запроса в очереди - позволяет увидеть скорость обработки запроса

**Выбор подхода к мониторингу**

В качестве подхода к мониторингу предлагаю использовать RED. Метод RED, фокусируется на трёх показателях: на частоте запросов, длительности их обработки и ошибках. Эти показатели помогают обеспечить стабильную работу веб-сервисов и API. Так как проблемные места сервиса связаны с API этот метод лучше всего подойдёт.

**Метрики**:

1. Количество заказов полученных через API - нужна для понимания внешней нагрузки на систему
